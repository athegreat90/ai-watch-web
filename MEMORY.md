Decisions and maintenance knowledge for AI Watch Web. Each entry says what was decided and why. Read this before changing anything. Update it when a decision changes.

Status on 2026-11-27: all 13 phases done. The plan was approved by the owner. There is no git repository, GitHub repository, image or release yet, and the feature pages are placeholders.

## Phase 3 results (API client, polling, connection state)

Built: `core/api` (models, `parseSnapshot`, `classifyError`, `StatusApi`, `sessionKey`, `statusOf`), `core/polling` (`poll`, `PAGE_VISIBLE`, `StatusPoller`), `core/connection-state`, `core/config` (`RuntimeConfig`, loaded from `/config.json` by an app initializer before the app starts). The shell header shows the connection state.

- **A row without id, agent or a string status rejects the whole response**, like the firmware. Other fields get defaults. An agent whose limits lack a window is dropped, not an error. `used_pct` is not clamped in the parser (the firmware clamps when it draws), so clamp in the view.
- **Backoff:** failure k waits `base * 2^(k-1)`, at most 30 s, with 20 % jitter that never passes the cap. Measured in a real browser against a server that was stopped and restarted: gaps of 2.9, 4.9, 10 and 23.6 s, then it recovered on its own. The worst case is about 30 s until it is live again, and a manual refresh skips the wait without overlapping a request in flight.
- **Status rules:** a response the app cannot read, or no success for 3 intervals, gives `stale`. Other errors give `offline`, `token-rejected`, `login-required` or `config-error`. The last good snapshot is kept through every error, and demo data never fills in.
- **`StatusPoller` reads the poll interval once**, when it is created, so the config must be loaded first. Phase 7 has to handle a changed interval (reload or a new poller).
- **`parse.ts` has no runtime imports** (only `import type`), so the contract test loads it directly with Node's type stripping. Do not add a runtime import to it.
- **Contract test** (`npm run test:contract`): 14 checks, all passing against a server built from the `ai-watch-server` source at `a495671`, not yet the pinned container (phase 9). It writes events and limits, refuses a non-local URL and does nothing without a token. It confirmed from the real server: query string gives 404, `OPTIONS` gives 501, limits for Gemini CLI give 400, `Cache-Control: no-store`, the documented order, `/api/status` capped at 8 sessions while `total_count` counts all, and `finished_long` and `waiting` computed by the server.
- **Dev proxy** (`proxy.conf.cjs`) forwards only the three read routes and takes the token from `AIW_DEV_TOKEN`. A write through the dev server returns 404.
- **In development `/config.json` returns 404** and logs one red console line. The defaults apply. The container creates the file in phase 8.
- **Bundle:** with HttpClient the initial bundle is 378.5 kB raw and 81.8 kB transferred. The raw warning budget moved from 350 kB to 450 kB and the error stays at 600 kB. The real goal is the 150 kB gzip target.
- **Checks:** 97 unit tests pass. Breaking the failure-counter reset made 3 poll tests fail, so they do catch regressions. The coverage table hides files at 100 %.
- **Not proven yet:** the proxy header and query stripping (phase 8), the stale rule in a real browser, and the contract test against the pinned server image.

## Phase 4 results (dashboard and sessions)

Built: `core/time/clock.ts`, `core/api/session-view.ts`, `core/connection-state/{snapshot-state,messages}.ts`, `core/polling/inject-poll.ts`, `shared/{status-badge,session-row}`, `features/dashboard`, `features/sessions` (list, detail and `SessionsFeed`), plus the sessions routes. The shell header, the dashboard and the Sessions pages all use the same connection logic.

- **One state machine for both endpoints.** `snapshotState(source)` holds what `ConnectionState` held in phase 3, and `injectPoll(fetch)` builds a shared poll. `StatusPoller` and `SessionsFeed` are thin users of them, so the Sessions page has the same offline, stale and recovery behaviour as the dashboard without a second loop.
- **`SessionsFeed` is provided by the `sessions` route**, not by root. The list and the detail page share one `/api/sessions` poll, and it stops when both are closed.
- **Local time:** `Clock.tick` is a monotonic signal that moves every second while the tab is visible. Only `working` and `needs_attention` sessions move on (`duration`, and `waiting` for attention). The server froze the others at their last update, so they must not tick. Times are counted from when the response arrived, so the browser clock cannot skew them.
- **Rounding:** the display can move up to 1 s at the moment a new response arrives, because the server sends whole seconds and the app floors the elapsed time. Measured in the browser: 4:39 to 4:47 over 8 s, with no double counting. The ±1 s is accepted.
- **Offline behaviour:** running times keep counting from the last good data while the server is unreachable, with the banner saying the data is old. Freezing them would be as wrong as letting them run, and the banner carries the warning.
- **Last update is a clock time** (for example 22:19:25) from the server's Unix seconds, shown in the viewer's time zone. It is not "N s ago", because comparing the server's timestamp with the browser clock would depend on clock skew. "Synced N s ago" is exact because it is counted locally.
- **Agent initials come from the name** (first letters of the first two words, or the first two letters of a single word). A new agent needs no registry entry. "Codex" shows "CO".
- **Detail page:** the route is `/sessions/:agent/:sessionId` and the pair identifies the session. If fresh data no longer has it, the page goes back to the list with `replaceUrl`, like the firmware. It waits for the first response before deciding, so a deep link does not bounce.
- **The dashboard lists up to 8 sessions** (the `/api/status` cap) while the counter shows the server's `total_count`. When there are more it says how many and links to the Sessions page.
- **Acknowledge is not on the detail page yet.** It arrives with the alerts in phase 5, where the acknowledgement key (agent, id, `updated`) is built.
- **Checked in a browser** against a server built from source and seeded with 7 sessions of every status: the order matches the server, "Needs you" is highlighted, "Took" stays fixed for a finished session, a deep link opens the detail, an unknown session goes back to the list, and the page is usable at 400 px. The header menu and the connection chip wrap onto several lines at 400 px, which is for phase 7 to polish.
- **Checks:** 187 unit tests pass, 96.6 % of lines covered overall. Making every session count as running made 8 tests fail.
- **Done later:** Playwright E2E for these pages, the pinned server image and axe checks (phase 9).

## Phase 5 results (alerts, celebration, limits)

Built: `core/attention` (`AlertTimer`, `AttentionService`), `core/celebration`, `core/limits/limits-view.ts`, `core/meeting/meeting-mode.ts`, `shared/{attention-overlay,celebration-banner,connection-banner}`, the Limits page, an Acknowledge button on the session detail page. The overlay and the banner live in the shell.

- **`AlertTimer` is a port of the firmware's**: fires when attention starts, again every 120 s from the last time it fired, and forgets everything when attention clears. Checked in a real browser: dismissed with Escape, it came back exactly 120 s after it was first shown, which matches "returns 120 s after it was shown".
- **Several sessions need you at once:** one dialog lists all of them. A session that needs you for the first time reopens the alert at once. A session that only changes its details does not.
- **Acknowledge is per state:** the key is (agent, id, `updated`). A new event for an acknowledged session asks again at once. Keys are kept in `sessionStorage` (latest 100). It never calls the server.
- **The alert is a native `<dialog>` opened with `showModal()`**, so the browser gives it a focus trap, Escape and a backdrop. The page behind is inert while it is open. Escape counts as Dismiss. The Dismiss button gets focus, and in Bootstrap's focus style it shows a bright grey fill that phase 7 should tone down for AMOLED.
- **The celebration is not modal**, so it can never block the alert. It lasts 4000 ms (measured in the browser), shows once per turn (key: agent, id, `started`), and keeps only the latest if two tasks finish together.
- **Celebration is skipped for good in a meeting**, not saved for later, and it forgets the previous snapshot after an error or a gap of more than three poll intervals. A finish that happened while the tab was hidden or the server was away is therefore not celebrated. Under reduced motion the message shows without the confetti animation (a change from the earlier plan, which said "skipped"; `FUNCTIONAL-PARITY.md` is updated).
- **Meeting mode is only a flag so far** (`MeetingMode.manual`). The switch and the focus timer arrive in phase 6, which must make `active()` also true while the timer runs.
- **Limits:** the three known agents always get a row, with "No usage data" when the server did not report them, because the server cannot tell "never reported" from "older than 15 minutes". Other agents the server reports are added after them. Used is clamped to 0–100 with one decimal. 70 % is amber and 90 % is red. The reset countdown runs locally and shows "Reset due. Waiting for new data." at zero, because the numbers are stale after a reset.
- **Visual bug the unit tests could not see:** Sass turned `#{$n}%` into `4 %` (with a space), the browser dropped the `left` rule, and all confetti fell at the same point. Found only by looking at it. The fix is `$n * 1%`.
- **Test trap with the server:** an event whose timestamp is not newer than the stored one is ignored with 200. Re-using a session id for a new "working" event after a "done" one does nothing. Use a new id.
- **Not done on purpose:** browser sound and desktop notifications. The plan marks them optional and off by default, and they need a settings screen and a user gesture, so they come with Settings in phase 7. The reduced-motion CSS was written but not checked in a browser.
- **Checks:** 305 unit tests pass (exit 0, no unhandled errors), 98 % of lines covered. Five deliberate breakages (no re-alert for a new session, acknowledgement ignoring `updated`, celebrating without seeing the session work, no gap rule, a repeat that never fires) each made tests fail.

## Phase 6 results (focus timer, meeting mode, idle robot, kiosk)

Built: `core/focus/focus-timer.ts`, `core/idle/idle.ts`, `core/kiosk/{pixel-shift,fullscreen,screen-wake-lock}.ts`, `core/connection-state/labels.ts`, `shared/idle-robot`, the Focus and Kiosk pages, and in the shell a timer pill, a Meeting badge and the dimming. `MeetingMode.active` is now manual or focus running.

- **Focus timer is counted from timestamps** (`Clock.wallNow()`), saved in `localStorage` key `aiw.focus`, and does not need the server. A hidden or sleeping tab cannot make it drift. A `setTimeout` records the end on time even in a hidden tab (the phase also turns `done` by itself when read). Reload keeps a running or paused timer, and a timer that ran out while closed shows as done.
- **Pause ends the meeting, so the alert returns at once.** Checked in a browser: running timer meant no alert and an amber Meeting badge (a session needed attention), pause brought the alert back, resume silenced it, reset brought it back. The firmware behaves the same ("fires again immediately after the meeting ends").
- **Meeting dimming is `opacity: 0.6` on the main content**, not hardware brightness. The header and the badge stay at full strength. The muted text is below 4.5:1 contrast while dimmed. That is accepted because the user chose to dim, but phase 7 should check it.
- **Idle:** 15 minutes without activity, only when no session needs you. Activity is pointer, key, touch, wheel, click, any change in the sessions or the connection state, or a session needing you. Timers and limit values moving do not count. The first touch, key or tap while idle only wakes the screen and the click that follows is swallowed for 600 ms. A mouse move wakes but is not consumed. The robot moves to another of four corners every 30 s. Meeting mode does not suppress it.
- **Real bug found by a unit test:** `touchstart` listeners on `document` are passive by default, so `preventDefault()` was ignored and a waking touch would also press what was under it. The listeners are now `{ capture: true, passive: false }`.
- **Real browser check of the 15 minutes** used Playwright's controllable clock. Not idle at 14:50, idle at 15:10, corners 0, 1, 3, 0, the waking tap on the "Limits" link did not navigate and the next tap did. One trap: with a fast-forwarded clock the real requests cannot answer before the simulated timeouts, so the connection state flaps and counts as activity. The check therefore ran with the API aborted so the state stayed "Offline".
- **Kiosk (`/kiosk`)** is outside the shell: big counters, up to 6 sessions, compact usage bars, no navigation. At 800x480 and 1024x600 it does not scroll (checked: scroll height equals window height), its buttons are 48 px tall, the pointer hides after 5 s and returns on movement, the picture shifts by 3 px every minute, and the Wake Lock was granted on `localhost` ("The screen stays on."). It re-requests the lock each time the tab becomes visible and releases it when closed.
- **Not verified:** real full screen (the test browser has no window and did not enter it, so only unit tests with a fake cover it), the Wake Lock on a plain-HTTP LAN address (the page says the browser cannot), a real Raspberry Pi, and the reduced-motion CSS.
- **Bootstrap outline buttons** filled with their colour on hover and focus, which is a large bright area on AMOLED. `_themes.scss` now gives them a quiet surface fill and keeps the coloured border and the light text. Phase 7 may refine it.
- **Test notes:** the idle constants (15 minutes, 30 seconds) are pinned in a test, because tests that use the constant itself cannot notice if it changes. One mutation (15 to 5 minutes) survived until that test was added. Seven deliberate breakages in total are now caught.
- **Checks:** 441 unit tests pass (exit 0, no unhandled errors), 92.6 % of lines covered. The kiosk template shows 0 % in the coverage table because of how the report maps an overridden component, but its tests render it.

## Phase 7 results (settings, themes, accessibility)

Built: `core/settings/settings-store.ts`, `core/theme/theme.ts`, `core/notify/notifier.ts`, `core/demo/{demo-data,demo-source}.ts`, the Settings page, a demo banner and a phone header in the shell, a global focus ring, and the `axe-core` dev dependency.

- **Settings** (`SettingsStore`, key `aiw.settings`): poll interval (2, 3, 5, 10, 30, 60 s), tone, desktop notifications. Demo mode is in `sessionStorage` (`aiw.demo`), so a new tab always starts with real data.
- **The poll interval is read once**, so a changed value applies after a reload. The page shows "Reload to apply" when the chosen value differs from the running one (`StatusPoller.intervalMs`). Checked in a browser: 10 s gave 2 requests in 12 s.
- **Theme:** `ThemeService` owns key `aiw.theme`, applies `data-theme` and `data-bs-theme`, and sets the `theme-color` meta tag. `public/theme-init.js` still sets it before first paint. "System" is dark or light, never AMOLED, and follows the operating system live (checked by switching the emulated colour scheme).
- **Demo mode** swaps only the data source (`DemoSource` in `StatusPoller` and `SessionsFeed`). The connection status reads `demo` and the shell shows a banner on every page, so example data cannot pass for real data. Toggling reloads the page, so nothing mixes. The demo has fixed sessions, and a long task that finishes 45 s in so the celebration can be seen (checked: it appeared after 44 s). It makes no request to the server. A server that is down still shows as down.
- **Tone and desktop notifications are off by default.** The audio is prepared from the Settings click, or from the first touch or key after a reload, because browsers only allow sound after a touch. Notifications need permission and a secure page, and the checkbox is disabled with an explanation otherwise. They fire when the alert comes up (not while it is already showing) and when the focus timer ends. Not verified with a real browser notification or real sound, only with fakes.
- **Accessibility, measured with axe-core 4.14 in a real browser** (WCAG 2 A and AA, 2.1, 2.2 AA and best practice rules): zero violations on all six pages in all three themes, with the alert open, with demo mode on, with meeting dimming, and at 400 px (no horizontal overflow). To repeat it, inject `node_modules/axe-core/axe.min.js` with Playwright's `addScriptTag` and run `axe.run()`. Phase 9 turned this into E2E tests (`e2e/a11y.spec.ts`). Against the container the CSP forbids inline scripts, so axe is run with `page.evaluate(source)`, not `addScriptTag`.
- **What axe found and was fixed:**
  - Bootstrap's `outline-secondary` text (`#6c757d`) was 4.47:1 on AMOLED, 4.03 on dark and 4.37 on light, and `outline-warning` (`#ffc107`) was 1.51:1 on light. Both now use the theme tokens.
  - The light theme's amber is `#8f5600` (was `#b36b00`, 3.9:1).
  - The skip link sat outside any landmark. It is now inside the header.
  - The kiosk had no `<main>` and no `<h1>`. It has both now.
  - **Meeting dimming broke contrast** (2.5 to 3.4:1 at 60 % opacity). It is now 70 % opacity, and `.dimmed` moves the muted, working, error (and in the light theme attention and done) colours the other way by the amount that keeps 4.5:1 after the dimming. If a token changes, the dimmed values in `_themes.scss` must be recomputed and re-audited.
- **Keyboard:** first Tab is the skip link, Enter moves focus to the main area, every control shows a blue ring (`:focus-visible`), and buttons have a two-ring shadow because Bootstrap removes the outline on `.btn`.
- **Responsive:** at 400 px the menu is its own row that scrolls sideways, with a thin scrollbar in the theme colours. The header went from a tall wrapped block to 115 px.
- **Bugs only a real browser showed:** my `.row` class in Settings collided with Bootstrap's `.row > *` (forced 100 % width) and the menu scrollbar was a white block. Both fixed.
- **Checks:** 580 unit tests pass (exit 0), 94.5 % of lines covered. Nine deliberate breakages were caught, including demo mode being ignored by the poller or the sessions feed, the status never saying demo, the user's interval ignored, a notification or tone without the user's consent, a repeated tone while the alert is showing, and the system theme turning into AMOLED.
- **Not verified:** real sound and desktop notifications, a real Raspberry Pi, real full screen, the idle robot under reduced motion, and the audit on a device with a screen reader.

## Phase 8 results (Nginx and Docker)

Built: `docker/Dockerfile`, `docker/entrypoint.sh`, `docker/nginx/{nginx.conf,site.conf,snippets/*}`, `.dockerignore` (allow-list), `compose.yaml`, `docker/test/entrypoint.test.sh`, `tests/proxy/{mock-upstream,proxy.test}.mjs`, and the scripts `docker:build`, `test:entrypoint`, `test:proxy`.

- **Base images, pinned by digest** (looked up from the Docker Hub registry API, not guessed): `node:26.13.1-alpine` and `nginxinc/nginx-unprivileged:1.30.6-alpine` (the stable branch). Both have amd64 and arm64. Phase 10's refresh script must update both digests.
- **The build runs on the build machine** (`--platform=$BUILDPLATFORM`) because the output is plain files, so the arm64 image needs no emulated npm build. `npm ci --ignore-scripts` is used.
- **Results:** 24.4 MB compressed (amd64), about 5.3 to 6 MiB of memory at rest, 4 processes, read-only root, user 101, `cap_drop ALL`, `no-new-privileges`. The arm64 image was built and tested under emulation (it reports `aarch64`).
- **How the secret travels:** a Docker secret file, read by the entrypoint, written into `/tmp/nginx/runtime.conf` (mode 600, owner nginx) as a `map` value. A test searches the image's real directories and finds the token in exactly two places: the mounted secret and that file. It is not in `docker inspect`, the process list, any response, the bundle, `config.json` or the logs. The access log format has the path without the query string and never a header.
- **The proxy decisions, all proven by tests against real containers (104 checks, amd64 and arm64):**
  - Only exact `GET /health`, `/api/status` and `/api/sessions`. Other methods give 405 before the server is asked. Everything else under `/api/` gives 404, including the write routes, dot segments and encoded slashes. Nothing for those ever reached the server.
  - **The query string is dropped by building the target from variables** (`proxy_pass http://$aiw_upstream$aiw_path`), not by a rewrite. It was proven with `?x=1` reaching the server as `/api/status`. The mutation that passes `$request_uri` instead breaks 7 tests.
  - **The proxy sends its own key and nothing of the browser:** a client's `X-Monitor-Key`, `Authorization`, `Cookie`, `X-Forwarded-For` and `X-Real-IP` never arrive.
  - **`X-AIW-Upstream-Status` works as designed:** 401 plus that header when the server refused the token, and no such header on Nginx's own basic-auth 401. Found while testing: the server's `X-Powered-By` also reached the browser, so it is hidden now.
  - **The server's name is looked up when needed** (a `resolver` plus variables), so the container starts before the server exists and answers 502 until it does.
  - **Timeouts:** 502 when the server is down, 504 when it is slower than 5 s.
- **The cache is 1 to 2 seconds, not 1.** Nginx counts in whole seconds, so an entry stored late in a second lives about 1 s and one stored early lives about 2 s. 12 simultaneous browsers cost the server at most 2 requests. Errors are not cached. `/health` is not cached. A cache hit has no `X-AIW-Upstream-Status` (nobody asked the server), which is fine because a 401 is never cached.
- **Real bugs found by the tests, not by reading:**
  - `$(printf '\n')` is empty in shell, so the newline guard matched everything and **every start was refused**. Fixed with a literal newline.
  - `grep` validates line by line, so `UPSTREAM_URL`, `RESOLVER` and `POLL_INTERVAL_MS` with a newline in them could have carried extra Nginx directives past a good first line. All values are now checked to be one line, with tests for the injection attempts.
  - `grep -r /var` inside the container hung on the log pipe. Every Docker call in the tests now has a time limit.
- **Checked in a real browser against the real image:** zero Content-Security-Policy violations (`securitypolicyviolation` listener plus the console), the dashboard goes Live through the proxy, a deep link to `/limits` works, the theme changes and persists, "Test connection" works, the kiosk renders, and `POST /api/events` and `/api/limits` from the page return 404. The red `/config.json` 404 of development is gone because Nginx serves it.
- **Compose:** `docker compose up` gives a healthy container (the Dockerfile health check), loopback-only port, 64 MB and 64 process limits. The released bundle in phase 12 uses a published image instead of `build`.
- **Mutation checks on the Nginx config** (rebuild the image, run the 104 checks): letting other methods through (18 fail), opening `/api/` (11), forwarding the browser's login (2), passing the query string (7), not sending the key (8), allowing inline scripts in the CSP (9), showing the Nginx version (1). All caught, all restored.
- **Not done or not verified:** the Sonar and Trivy scans of the image (phase 10), the CI workflows that build and publish both architectures (phase 11), a real Raspberry Pi, a real AI Watch server behind the proxy (the tests use a stand-in that follows the documented contract, and the contract test already checked that contract against the real server), and Docker Desktop was started by hand for this phase.

## Phase 9 results (test suites)

Built: Playwright 1.65.1 (Chromium), `playwright.config.ts`, `compose.test.yaml`, `e2e/` (13 spec files, 112 tests, one worker), `e2e/tsconfig.json`, scripts `e2e`, `e2e:install`, and `typecheck` now includes `e2e`. `@types/node` was added for the tests.

- **What it runs against:** the real image (`ai-watch-web:test`, built if missing) in front of the real AI Watch server release **v1.1.4**, pinned by digest `sha256:26c92877…c9bd` (amd64 and arm64) in `compose.test.yaml`. A random token is written to `e2e/.run/` (git-ignored) on every run. A second web container with a wrong key covers "token rejected". The server on main is 6 commits ahead of v1.1.4 but they only touch CI, docs and security scripts.
- **Isolation:** every test restarts the server (it keeps everything in memory) and the web container (its 1 to 2 s cache would otherwise serve the previous test's data). A `problems` fixture fails a test on any console error, script error or CSP violation.
- **Covered:** dashboard, sessions and detail, limits, NEEDS YOU alert (repeat after 2 min, acknowledge, reload, focus), celebration, focus timer, meeting mode, idle robot, kiosk at 800x480 and 1024x600, themes (AMOLED default even with a light system, `system` never AMOLED, no shadows or gradients), settings, demo mode, connection states (server down, never up, hidden tab, 3 s rhythm, token rejected), the proxy rules, security headers, cache headers, token never in any answer, axe on 6 pages + detail + alert + meeting dimming in 3 themes, and the contract test against the real server.
- **Mutation checks of the E2E suite:** passing the query string (2 fail), inline scripts in the CSP (1), opening `/api/` (1), kiosk spacing not compacted (1), alert never repeating (1). All caught.
- **Real findings, by running against real data:**
  - **The kiosk scrolled at 800x480** with 6 or more sessions (6 px) and with 7 or more (49 px, the "+ N more" line). Phase 7 had only checked it with fewer sessions. Fixed in `kiosk.scss` with a `max-height: 520px` media query (row padding, counter size). The row count stays 6 so "+ N more" is true.
  - **The server keeps at most 40 sessions** (`MaxSessions`), the same as it lists, so "N more are not listed" on the Sessions page can never appear against it. The message stays for safety.
  - **`started` is per turn and `duration` of a finished task is `updated - started`**, so a test can make a "long task" by sending the working event with a timestamp 400 s ago, then the done event now.
  - **Nginx resolves `..` and `//` before routing.** `/api/%2e%2e/health` is `/health`, `/api//status` is `/api/status`, and `/api/%2e%2e/events` is a file of the app (POST gives 405). None reaches a write route.
  - `/config.json` is `no-store` (stricter than the `no-cache` the plan said), and it is `{}` unless `POLL_INTERVAL_MS` is set.
- **Test bugs I made and fixed (so they do not come back):**
  - The helper `open()` waited for the connection chip to stop saying "Connecting…", but before the first render the chip is empty. It returned before the first answer and the celebration test sometimes posted "done" before the page had seen "working", so there was no edge and no celebration (3 of 30 runs). It now waits for a non-empty text, and the tests wait to see "Running".

## Reference facts (verified in source)

Analysed on local copies of the three repos. They were not compared with GitHub heads: server `a495671`, firmware `97bb7c9`, hooks `646f476`. Re-diff them in phase 1.

### Firmware (`AIWatch.ino`, `AlertTimer.h`, `FocusTimer.h`)

- It polls only `GET /api/status`, 3000 ms after each fetch ends, sending only `X-Monitor-Key`. It never calls `/health` or `/api/sessions`. No retries, no persistence, no sound, no battery readout, no demo data.
- Non-200 clears all sessions and limits. 401 shows "check token". More than 8 sessions or a row without `session_id`, `agent` or string `status` is rejected.
- Session identity is (agent, session_id). Ordering comes entirely from the server.
- NEEDS YOU repeats every 120 s. A tap only hides it. Only Acknowledge in Detail stops it, keyed by (id, agent, `updated`), and it is lost on reboot. `docs/SCREENS.md` says otherwise and is wrong.
- Celebration: same agent and id going working to done between two polls, `finished_long` true, meeting off, 4000 ms. If the working state was never seen, nothing fires. A finish during meeting mode is skipped for good.
- Meeting mode (manual or focus running) dims to brightness 40 and suppresses alert and celebration. It does not suppress the 15-minute idle robot.
- Limits: Claude Code, Codex, Antigravity. Bars turn amber at 70 % and red at 90 %. `resets_in` is not ticked locally.
- Focus timer: 25 minutes, no completion sound. "Offline preview" shows offline texts only, with no mock data.

### Server (`handler.go`, `monitor.go`)

- Only exact `GET /health` is public. `/api/status` (max 8 sessions) and `/api/sessions` (max 40) need `X-Monitor-Key`, compared in constant time. The token needs at least 24 characters and lives in `config.local.json`.
- Routing uses the full `RequestURI`, so `/api/status?x` returns 404. Auth is checked before the path.
- No CORS. `OPTIONS` and other methods return a plain-text 501. 16 concurrent connections, 3 s timeouts, no keep-alive, no rate limit. Responses carry `Cache-Control: no-store`.
- `/api/limits` accepts Claude Code, Codex and Antigravity (`monitor.go:247`). `docs/API.md:39` lists only two and is stale.
- `finished_long` is `done` and duration at least 300 s, computed on the server.
- TTLs: done, idle, notice and error 120 s; working and needs_attention 3600 s; limits 900 s. State is in memory only.
- Event timestamps must lie within now minus 3600 s and now plus 60 s. An event with an older timestamp than the stored one returns 200 and is ignored.
- The published host port binds `127.0.0.1` by default.
- The hooks also send "Gemini CLI" and "GitHub Copilot CLI" sessions. They have no limits.

## Decisions

1. **One Nginx image with a same-origin proxy.** The browser never sees the token and there is no CORS to configure. The server has no CORS and answers `OPTIONS` with 501, so a direct browser call would not work anyway.
2. **No backend, database or state library.** The app only reads three endpoints. Signals and RxJS are enough.
3. **Poll `/api/status` like the firmware (3 s after completion), and `/api/sessions` only on the Sessions page.** This keeps requests near 20 per minute per client and matches what the firmware does.
4. **Tick `duration`, `waiting` and `resets_in` locally from fetch time, on a monotonic clock.** Using the browser's wall clock against server timestamps would show wrong times when the clocks differ.
5. **Keep server order.** Re-sorting in the client would diverge from the firmware and the server.
6. **Celebration uses the firmware's edge detection plus a Set keyed (agent, id, `started`).** The Set stops repeats when polling returns the same state again.
7. **Demo mode, focus-timer sound and the `/api/sessions` page are new.** They are not firmware behaviour. Sound is off by default and needs a click because of autoplay rules.
8. **AMOLED is the default theme, whatever the OS prefers.** The owner asked for it. Dark, light and system stay in Settings. The default is set in `index.html` and applied by an external script, because the CSP forbids inline scripts.
9. **Query strings are stripped in the proxy.** Nginx appends the request args to a literal `proxy_pass`, so each proxy location uses an exact match and `rewrite ^ /api/status? break;`. This was decided from Nginx's documented behaviour and must be proven by a test in phase 8.
10. **The token is validated before it is written into Nginx config.** It must match `[A-Za-z0-9._~+/=-]{24,}`. A `"`, `;`, `\`, `$` or newline would break or change the config, because Nginx expands `$` inside strings.
11. **Two kinds of 401 are told apart by a header.** The proxy adds `X-AIW-Upstream-Status: $upstream_status` with `always`. It is set only when the server answered. A remapped status code was rejected because it would also catch Nginx's own basic-auth failures.
12. **CSP keeps `'unsafe-inline'` for styles only.** Angular injects component styles at runtime. The build sets `inlineCritical: false`, because the inlined critical CSS needs an inline `onload` handler that the policy would block. Scripts are never inline. Fonts are self-hosted.
13. **Optional 1 s microcache on `/api/status`.** It protects the 16-connection server from many tabs. It needs `proxy_ignore_headers Cache-Control Expires` and `proxy_cache_lock on`, because the server sends `no-store` and Nginx would otherwise skip caching. It is the one documented exception to "no caching".
14. **Dashboard access control is a separate problem from token hiding.** Default is a loopback bind, with optional basic auth through a secret `htpasswd`, and Tailscale or an authenticating proxy for remote use.
15. **Build the static files on `--platform=$BUILDPLATFORM`.** The output is the same on every architecture, so arm64 needs no QEMU build step.
16. **Version the release the way `ai-watch-hooks` does.** `CHANGELOG.md` headings declare a minor or major version, which fixes the server's rule that starts at `v1.0.1` and has no such mechanism. First version is `v0.1.0`.
17. **Reuse the server's release scripts.** `automatic.py`, `push-image.sh`, `require-ci.sh`, `assets.sh` (without the Go loop), `check-image.sh`, `check_findings.py`, `upsert-issue.sh`, `smoke.sh`, `refresh_base.py`, `check_version.py`. Change the shipped-file list and the base images only.
18. **Extras beyond the server's pipeline are proposals.** Secret scan, filesystem and misconfiguration scan, SBOM, `npm audit` and CodeQL (if the repo is public) do not exist in the server repo.

## Gotchas

- A container cannot reach a server that publishes `127.0.0.1:8765` through the host. Use a shared Compose network (optional overlay in the bundle) or a LAN address.
- Wake Lock and notifications need a secure context. `http://localhost` counts. A plain-HTTP LAN address does not.
- Audio needs a user gesture.
- Do not take npm "latest" for TypeScript. On 2026-11-26 it showed 7.0.2, which Angular may not support. Use the range in Angular's peer dependencies.
- Versions seen on 2026-11-26: Angular CLI 22.3.0 (Node `^22.22.3 || ^24.15.0 || >=26`), Bootstrap 5.3.9, Playwright 1.65.1. Re-verify when scaffolding.
- Contract fixtures: use relative timestamps, because events outside the window now-3600 to now+60 return 400.
- The server's `remediate.yml` creates its issue without `gh issue --search`, because the search API returned nothing for an App installation token. The firmware repo still uses search, so do not copy from it.
- Sonar runs only on non-PR events, so pull requests get no Sonar gate. Same as the server.
- Use the Tailscale trust credential's immutable-ID subject format. The short repository name is rejected with 403.

## After the first push (2026-11-27)

What happened once the repository existed, and why. The earlier "nothing has run on GitHub" notes describe the state before this.

- **The repository was created and pushed** by the owner's request: public (like its three siblings), seven conventional commits, no AI attribution. A secret and personal-data scan came first.
- **Rule: never push to `main`.** Always a branch and a pull request; the owner merges. `main` is protected (pull request, up to date, conversations resolved, no force push or deletion, also for administrators; 0 approvals because one owner cannot approve their own pull request). Required checks: `node`, `e2e`, `static`, `images (amd64)`, `images (arm64)`, `release-script`, `deploy`, `analyze`. `sonar` and `release-eligibility` are not required because they only run after a merge.
- **The first CI run failed in `e2e`, and the cause was the test harness, not the app.** The proxy tests reached their stand-in server through `host.docker.internal` from `--add-host`. Nginx resolves `UPSTREAM_URL` with its own resolver, which does not read `/etc/hosts`, so on the Linux runner every data route answered 502 (Docker Desktop answers for that name itself, which hid it). A failing assertion also left a mock open and Node hung until the 30-minute timeout. Fixed (pull request #1): the tests use the host-gateway address, and the mock calls `server.unref()`.
- **Sonar over Tailscale needed two things:** a trust credential whose subject is the immutable form `repo:athegreat90@<owner id>/ai-watch-web@<repo id>:ref:refs/heads/main` (the short form gives 403), and `SONAR_HOST_URL=http://<tailnet ip>:9000`. A value with no scheme and no port made `curl` go to port 80, which the ACL (only `tcp:9000`) silently drops, so it looked like a timeout.
- **`v0.1.0` did not come out of the first green run.** The release only starts for a push that changes a shipped path, and the merge of #1 changed only tests and `CLAUDE.md`. The version in `package.json` was still `0.0.0`; bumping it (pull request #2, `package.json` and the lockfile) made the automatic release run. Result: tag, GitHub release (bundle zip, two SBOMs, `SHA256SUMS`), and `ghcr.io/athegreat90/ai-watch-web:v0.1.0` for amd64 and arm64 with `:latest` at the same digest; anonymous pull works. Version tags are immutable.
- **`compose.standalone.yaml`** (a pull request after that): the page as one Compose file for a server that already runs, no `build`, `UPSTREAM_URL` required (the bundle's default name only exists next to the server), no `extra_hosts` (it does nothing for Nginx on Linux). It sits at the repository root and not in `deploy/`, and its test is not an npm script, both on purpose: `deploy/` and `package.json` are shipped paths and would have made a release for no change in what runs. Tested alone in an empty folder with the real published `v0.1.0` image, and `tests/standalone/standalone.test.sh` runs in the `e2e` job.
